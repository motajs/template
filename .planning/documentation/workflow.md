# 指南文档编写流程

## 总则

指南文档按三个阶段推进，不得跳阶段：

1. 讨论阶段：确定要写什么、分成几篇。
2. 文档骨架：每篇先写人类可读的骨架，检查并修订，交由用户审阅。
3. 文档编写：骨架获用户明确确认后，才开始写正文，并进入用户审阅循环。

文档正文必须由子代理编写或修改，主代理不得内联落盘（阶段 CONTEXT 的豁免条款除外）。任何阶段都不得提前写正文。

## 阶段一：讨论

### 输入

用户给出需要写成文档的内容、目标读者和大致范围。

### 讨论内容

- 这批内容要解决什么问题。
- 应该拆成几篇文档，每篇的边界是什么。
- 每篇的目标读者、前置知识和阅读顺序。
- 哪些内容写进文档，哪些留给其他篇目或后续阶段。
- 哪些内容适合代码示例、mermaid、效果图、live。
- 哪些术语需要专门解释。

### 输出

一份文档清单，包含：

- 每篇文档的暂定标题和文件路径。
- 每篇的职责与不负责的内容。
- 与其他文档的衔接关系。
- 尚未决定、需要用户裁决的问题。

### 约束

- 讨论阶段由用户主导。主代理先听用户说明，不抢先用子代理探索需求或自行拆分。
- 讨论没有确认文档拆分前，不进入骨架阶段。
- 不写标题以外的正文，不写示例，不写 live。

## 阶段二：文档骨架

### 骨架目标

骨架是写给用户审阅的文档设计图，不是正文草稿。它要让人一眼看出这篇文档准备怎么教、每一节讲什么、示例和 live 放在哪里、哪些内容明确不写。

骨架必须人类可读，避免把提示词、长篇分析或源码摘录塞进去。

### 骨架文件位置

默认放在当前阶段的 `skeletons/` 下：

```text
.planning/phases/<phase>/skeletons/<doc-slug>.md
```

如果当前任务不属于某个阶段，放在 `.planning/documentation/skeletons/<doc-slug>.md`。

### 骨架格式

每篇骨架使用以下结构。标题层级最深到三级，骨架本身不展开正文。

```markdown
# <文档标题> 骨架

## 文档信息

| 项目         | 内容                                            |
| ------------ | ----------------------------------------------- |
| 文件路径     | `docs/.../xxx.md`                               |
| 目标读者     | ...                                             |
| 前置知识     | ...                                             |
| 前后衔接     | 上一篇讲什么；本篇接什么；下一篇讲什么          |
| 本篇目标     | 读者读完后能做什么                              |
| 不负责的内容 | ...                                             |
| 状态         | 骨架待审 / 骨架已确认 / 正文编写中 / 待用户审阅 |

## 读者问题

- 读者读这篇之前通常会问什么。
- 读完后应该能回答什么。
- 哪些问题明确不在本篇回答。

## 章节结构

### 1. <章节标题>

- **目的**：这一节要让读者明白什么。
- **内容**：要讲的概念、机制、接口和步骤。
- **衔接**：上一节留下什么问题，这一节如何接上。
- **重点**：读者最需要记住的内容。
- **不写**：这一节明确不展开的内容。

#### 1.1 <三级标题>

- **目的**：...
- **内容**：...
- **示例**：几个；每个示例是什么；是完整示例还是最小示例。
- **live / 图**：是否需要；展示时间轴、播放效果、结构还是流程。
- **术语**：需要解释哪些词。
- **衔接**：讲完后如何进入下一节。

### 2. <章节标题>

...

## 示例计划

| 编号 | 所在章节 | 示例是什么 | 示例目的 | 代码范围                    | live / 图 | 放在哪里 |
| ---- | -------- | ---------- | -------- | --------------------------- | --------- | -------- |
| E1   | ...      | ...        | ...      | 完整类 / 最小片段 / 完整 UI | ...       | ...      |

## live 计划

| 编号 | 所在章节 | 展示内容 | 类型                         | 与正文的关系 |
| ---- | -------- | -------- | ---------------------------- | ------------ |
| L1   | ...      | ...      | 时间轴 / 播放效果 / 结构交互 | ...          |

## 图表计划

| 编号 | 所在章节 | 图类型                    | 要说明的结构或流程 |
| ---- | -------- | ------------------------- | ------------------ |
| D1   | ...      | mermaid / 效果图 / 白板图 | ...                |

## 术语表

| 术语 | 首次出现位置 | 普通解释 | 是否必须使用              |
| ---- | ------------ | -------- | ------------------------- |
| ...  | ...          | ...      | 是 / 否，能否换成普通说法 |

## 内容边界

- **必须写**：读者完成任务必需的内容。
- **可以简写**：只需一句带过的内容。
- **明确不写**：内部实现、罕见边界、其他文档已讲清的内容。
- **留给其他文档**：哪些内容转到哪一篇。

## 验收标准

- 读者读完后能完成什么操作。
- 读者应该能复述哪些模型或状态关系。
- 哪些示例必须能独立运行。
- 哪些 live 必须真实反映行为。

## 未决问题

- 需要用户裁决的拆分、命名、范围或示例选择。
```

### 骨架检查

骨架完成后，派第二个子代理检查。检查者只做两件事：

1. **内容合理性**：该讲的有没有讲，不该讲的有没有写；章节顺序、示例数量、live 和图表是否服务目标；有没有明显的内容缺口或越界。
2. **规范符合性**：是否违反 `guide.md`、本流程和当前阶段 CONTEXT 中的文档要求，包括标题、读者取舍、接口引入、示例完整性、术语解释、live 放置和边界处理。

检查结果写回骨架末尾或独立检查记录，至少包含：

- 阻断问题。
- 非阻断建议。
- 是否符合规范。
- 需要用户裁决的问题。

### 修订循环

- 根据检查结果修订骨架。
- 修订后再次检查。
- 最多循环三次。
- 三次后仍有阻断问题，停止并汇报具体问题，不再自行循环。

### 用户审阅

骨架通过内部检查后交给用户审阅。用户确认前不得开始写正文。

用户审阅的重点是：

- 文档拆分是否合理。
- 章节是否覆盖目标，是否有明显多余内容。
- 示例、live 和图表是否足够且位置正确。
- 读者关心与不关心的内容划分是否正确。
- 标题和术语是否符合预期。

## 阶段三：文档编写

### 开始条件

必须同时满足：

- 骨架已通过内部检查。
- 用户已明确确认骨架。

未满足时不得编写正文，也不得派发正文编写子代理。

### 编写要求

- 按骨架写，不擅自增删章节或改变文档拆分。
- 先读 `guide.md`、当前阶段 CONTEXT、目标文档之外的全部现有文档，再读目标文档和相关源码。
- 复杂接口按“为什么 → 获取什么 → 最小示例 → 说明 → 下一步”的顺序写，不能写成 API 参考。
- 每个示例前说明它是什么；示例后说明发生了什么。
- live 就近放置；复杂时序优先拆时间轴和播放效果两个视角。
- 只写对使用有帮助的行为模型，不写内部实现和罕见边界。
- 标题使用短名词短语，不写步骤式或口语化标题。
- 写完跑 prettier、文档构建和死链检查。

### 用户审阅循环

- 骨架阶段由用户审阅骨架；正文阶段由用户审阅最终文档。
- 用户提出意见后，由子代理逐条修改；不擅自扩大修改范围。
- 循环直到用户明确表示满意。
- 用户确认前不宣称完成，不写 SUMMARY，不更新 ROADMAP 或 STATE，不提交。

## 角色分工

| 角色       | 职责                                                     |
| ---------- | -------------------------------------------------------- |
| 用户       | 主导讨论、确认文档拆分、审阅骨架、审阅最终文档、裁决争议 |
| 主代理     | 组织阶段、派发子代理、汇总检查结果、保证流程不跳阶段     |
| 骨架编写者 | 按模板写人类可读的骨架                                   |
| 骨架检查者 | 只检查内容合理性与规范符合性，不改正文                   |
| 文档编写者 | 按已确认骨架写正文，按用户意见修订                       |

## 子代理上下文包

每个新任务必须新开子代理，不得复用已完成任务的子代理会话，避免上下文污染。唯一例外：子代理因规则冲突或安全限制在读取、修改前提前返回，可以续用该未执行会话。

每次派发文档子代理前，任务提示必须包含以下上下文；缺任何一项都不得派发：

- 必读 `.planning/documentation/guide.md`。
- 必读 `.planning/documentation/workflow.md`。
- 必读当前阶段 CONTEXT，例如 `.planning/phases/10-docs-restructure/10-CONTEXT.md`。
- 涉及正文修改时，按 D-115 读完全部现有文档，并说明阅读目的；任务中写明阅读范围，子代理回报实际读过的文档与结构判断。
- 目标文件的完整路径，以及明确禁止修改的文件范围。
- 需要核对的源码路径；内容写作任务必须核对源码，不能只读旧文档。
- 本次要解决的问题、验收标准、需要运行的格式化与构建命令。
- 明确禁止 commit，除非用户当次明确要求。
- 明确要求子代理先完成阅读，再开始修改；未读或未说明阅读范围即视为不合格。

骨架检查子代理的上下文包额外包含：

- 目标骨架文件路径。
- 本次骨架对应的文档拆分与用户已确认的边界。
- 检查只做内容合理性与规范符合性两件事，不直接改正文。
- 输出阻断问题、非阻断建议、规范结论和需要用户裁决的问题。
