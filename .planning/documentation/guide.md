# 指南文档编写规范

## 适用范围

本规范适用于 `docs/` 下面向使用者的指南文档，包括教程、渲染指南、系统说明和扩展说明。API 自动生成页、计划文档、流程记录不直接适用本规范。

阶段 CONTEXT 中的局部决策优先于本规范；本规范负责沉淀所有指南文档通用的写作要求。`guide.md` 与 `workflow.md` 是文档工作的统一入口。

## 文档目标

文档的目标是让读者能完成任务，而不是展示作者知道多少。

- 读者读完应知道怎么用、怎么改、怎么写能运行，以及常见错误怎么处理。
- 原理只讲到“足够正确使用”为止；读者不需要的实现细节不写。
- 文档不是源码导读，不逐段解释源码，也不按代码目录或接口清单组织。
- 内容重心由内容性质决定：现成能力重点讲怎么用，扩展机制重点讲怎么自定义。

## 读者与取舍

- 先判断目标读者是谁、读者已经读过什么、这篇文档要解决什么问题。
- 只写读者真正需要知道的内容。能删就删，不追求面面俱到。
- 不写罕见边界、极低概率异常、需要刻意构造的情况。
- 不写“我之前改好了”“文档站没有环境”“不要现场 new Texture”这类修复过程、问题复盘或元叙述。
- 不把用户提出的问题、审阅意见或“为了解决问题所以这样写”抄进正文。
- 不写“源码怎么怎么样”。除非某段行为模型是理解用法所必需的，否则不要讲实现。
- 必须讲的行为模型要讲清，例如状态机如何读取状态、曲线如何把时间进度映射为数值变化。
- 可以写应用场景，但必须能从接口语义、限制或代价推导出原因；不得凭空写“常用于”“只用于”。
- 不假设某个曲线、模式或接口适合什么场景；只客观描述形状、速度和端点行为。

## 结构顺序

按读者的理解顺序组织，不按代码目录或 API 清单组织：

`问题或场景 → 系统模型 → 机制与原因 → 接口与用法 → 示例 → 少量边界 → 总结`

- 讲一个系统时，先讲模型是什么（概念、组成、角色、数据流），再讲接口。
- 每个章节只回答一个问题；不同消费者、不同阶段分开讲。
- 只在认知跳跃大的地方用一两句话承接，不硬加“接下来我们……”式过渡。
- 复杂接口必须按使用顺序拆开：为什么需要 → 先获取什么 → 最小示例 → 示例做了什么 → 下一步做什么 → 再给下一个示例 → 最后才是完整用法。
- 简单接口可以短，但不能只列签名。
- 模板不要放在开头。先讲概念和扩展点，再给引导语、模板代码、模板说明。
- 只有读者需要自己实现接口或注册内容时才给模板；纯接口使用只给示例。
- 纯内部实现章节要靠后，并明确本章讲的是内部实现；文档前半部分先讲怎么用。
- 高级教程按库文档方式写，可用示例加解释；中级教程的“复制什么 / 改什么”六步法不要套到高级教程。

## 标题

- H2/H3 一律使用短名词短语。
- 不用句子、祈使句、问句，也不用“标题：一句解释”这种冒号扩展。
- 标题只说明“这一段讲什么”，不承担章节摘要的作用。
- 不写“第一步”“用 set 让它动起来”“拿到控制器”这种步骤式或口语化标题；步骤放在正文列表里。
- 文件名与目录名使用连字符英文命名。

## 接口讲解

每个接口、成员或类型第一次出现时，按以下顺序说明：

1. 为什么当前场景需要它；不用它会缺什么。
2. 它的名称、类型或形态。
3. 它的用途和关键限制。
4. 最小示例或参数说明。

不得上来就贴签名、参数表和“它能做什么”。不得只列接口名并假设读者已经知道。

- 只写用户会使用的接口；引擎内部接口、内部成员不写进用户文档。
- 常用接口放主要位置，不要塞进“其他接口”。
- 状态驱动的系统必须讲清：哪些操作改变状态，哪些读取操作默认读取哪一个状态。
- 源码注释与实现不一致时，以方法注释为准，并在对话中报告；不把不一致写进正文。
- 编辑器、`.jsonc` 等尚未完全就位的内容，按“编辑器已经完成”写；不要写过渡做法。

## 示例与 live

### 代码示例

- 示例必须完整、结构正确，能与上下文一起运行；不要给脱离上下文的成员片段。
- 类、函数、文件级片段要保留完整结构；必要时用注释省略无关部分。
- UI 示例遵循项目标准模板；完整示例包含 imports、props、组件和 `FULL_LOC`，简化示例使用 `// setup` + `// 组件内容`。
- `value` 双向绑定统一写 `v-model:value`；其他 prop 写 `v-model:prop`。
- 教程中的实操按“目标 → 改哪里 → 复制什么 → 改什么 → 怎么验证 → 注意”组织；示例取最短可行路径。
- 内容较杂的功能按功能拆分示例，一个功能一段，不合并成一大块。
- 每个示例前说明它是什么、要演示什么；不要突然丢代码。
- 完整代码放在最后；前面用最小示例逐步建立。

### 注释

- 注释解释当前状态、意图、结果或关键行为，不逐行翻译语法。
- 复杂流程的链式代码可在行尾注释当前对象、索引、锚点和本行作用。
- 注释服务于理解；不要为了“注释多”堆无信息量的句子。

### live 与图

- live 放在对应知识点旁边，不能只在文末放一个综合 live。
- 需要看效果的接口、属性、状态变化各自配 live；复杂时序优先拆成“时间轴”和“播放效果”两个视角。
- 动画、交互、状态变化不要用 CSS 定时器伪造；使用真实执行器。
- 渲染树、事件流、数据流、状态机、组件拆分、完整示例步骤等结构或流程，用 mermaid 图表达；图放在机制小节开头或示例前，配一两句说明。
- 视觉变化、布局、材质、几何关系适合用效果图或白板图；数字堆砌不能代替可视解释。
- 不要把多个互不相同的示例塞进一个 live；一个示例至少有一个独立 live。

## 语言与术语

- 用普通开发者能直接理解的中文；优先短句和具体动作。
- 专用名词首次出现必须解释它是什么、在这篇文档里指什么；能不用术语就不用。
- 不引入“插值”“句柄”“上游/下游”等未解释术语；必须使用时要给出普通解释。
- 可读性优先于形式上的绝对准确；不为了准确堆复杂公式、限定条件或底层计算。
- 不写“适合位移/淡入淡出/蓄力/脉冲”这样的用途假设；只写客观形状和效果。
- 加粗内容不要以标点开头或结尾，避免 CommonMark 边界导致不渲染。

## 边界与注意事项

- 边界与特殊情况集中放在文末，不混入主干。
- 只写真正会影响使用、容易触发或容易误解的问题。
- 不重复正文已经讲过的流程，不写“必须先选择对象”这种显而易见的提醒。
- 不写没有依据的约束，例如“计划定义完要尽快 planEnd”。
- 如果没有值得写的边界，就不开这一节，不要为了章节完整而凑内容。

## 正确性与验证

- 写文档前先理解完整设计、调用链和生命周期，不只读被讲到的一段代码。
- 每次修改前按站点阅读顺序读完目标之外的全部现有文档；目的是理解分工和写作风格，不是只读目标页。
- 写之前核对源码、接口、默认值、可空性和实际行为；构建通过不等于语义正确。
- 写完后跑 prettier，再跑文档构建，检查死链。
- 修订循环不逐轮提交；用户明确确认后再统一提交。

## 审阅流程

1. 骨架检查：第二个子代理只检查内容合理性和规范符合性；最多修订三次，仍不通过则停止汇报。
2. 用户审阅：骨架和最终文档都由用户审阅；用户按自己的阅读体验提出意见，AI 只改用户点名内容。
3. 审阅只分骨架检查和用户审阅两层；用户确认前不宣称完成。

## 参考文档

`.planning/references/feishu-teaching-docs/` 中的教学文档只用于观察行文思路、信息密度、示例和图示的放置方式，不是内容模板，也不是当前项目文档的正确性来源。

参考时重点看：

- 开头先给目标和效果，再进入步骤。
- 概念之后马上给最小示例，示例之后说明发生了什么。
- 视觉变化用效果图或图解释，不靠文字堆。
- 暂时不需要的底层内容明确后置，不为了完整而展开。
- 结尾有总结和下一篇的衔接。

不要照搬参考文档的编号、标题风格或具体结构；当前项目仍按本规范和阶段 CONTEXT 执行。
