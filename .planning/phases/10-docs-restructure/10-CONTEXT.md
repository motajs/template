## Phase Boundary

重构过老、结构不佳、新人理解难度过高的项目文档。面向多背景读者（完全新手 / 不懂代码的作者 / 有基础的作者 / AI Agent）提供分层指南，并专门为 AI Agent 编写参考文档。

**执行方式（本阶段关键）：** 引擎大部分接口已定稿、短期内不会大改，但编辑器、部分重构与整体收尾尚未完工，故本阶段采用**伞阶段 + 增量派发**：用户每次派发一个具体小任务，AI 据此在 Phase 10 下创建独立计划并执行（Plan → Execute → Verify），做完再由用户派发下一个。**已定稿、可先行的部分先做**；未完工部分（初级文档、高级教程、未定稿接口等）挂起，待条件成熟后由用户再派发。

文档分为六大部分：

1. **总览**：如何正确地看文档、查文档；不同背景的作者应如何阅读；AI Agent 应如何阅读。
2. **初级文档**：面向完全新手，**不含任何代码**，教学编辑器基本操作，并提供一些**仅使用编辑器的非代码编辑功能**即可实现的效果。因编辑器尚未实装，**待编辑器实装后再规划**。
3. **中级教程**：面向读完初级文档的作者及有一定经验的作者，讲解**必须使用代码**才能完成的内容，简单讲解顶层接口的使用，**不深挖底层逻辑**。读完本部分，作者理应能完成绝大多数需求。
4. **高级教程**：面向有高度定制需求、以及需要理解底层逻辑的作者，**系统讲解引擎的设计理念**。**待引擎整体完工后再规划**。
5. **API 参考**：列出引擎的所有 API 接口并给出解释，**重点接口详细解释**。
6. **Agent 参考**：面向 AI Agent，包含引擎快速总览、需求接口定位、游戏数值设计、游戏地图设计等参考文档。

### 验收与流程

- **D-09:** 验收标准 = **用户人工审阅** + **链接全部有效** + **构建通过**。
- **D-10:** 本阶段采用**增量派发**：用户每次派发一个具体小任务，AI 只针对该任务在 Phase 10 下创建独立计划；不得预先把整个阶段规划到底。可先行部分先做，未完工部分挂起待派发。

### 执行方式（本阶段特有，优先级最高）

- **D-11:** 阶段计划随任务累积，可反复追加/重规划；新任务到来时可新增计划而不必重排既有计划。
- **D-12:** 每个计划执行前，第一个 block 点必须**先向用户汇报计划内容**（要做什么、为什么、大致怎么做、影响范围）并等待用户明确回复「可以执行」；未收到「可以执行」前不得开始该计划的任何一步，也不得派发执行子代理。
- **D-13:** 新增或修改任何公共、受保护、私有方法/字段等命名，以及文档目录/文件名，均**必须先向用户反馈并获批准**后方可使用。
- **D-14:** 每个任务的范围由用户界定；AI 不擅自扩大范围。发现的越界内容只记录、不实施。

### 中级教程（第一批派发内容：`docs/intermediate`，24 篇）

**总原则**

- **D-15:** 本批只写**中级教程**；面向「读完初级 / 只懂一点代码的作者」。只讲**必须用代码完成**的内容与**顶层常用接口**，不深挖底层原理；**底层 / 不常用接口不讲**（留高级教程）。
- **D-16:** **不写**「渲染端教程后续再讲」这类元叙述；**假设渲染端教程已存在**，指向渲染端内容时如指向一个平行部分。
- **D-17:** 全文**适当加跳转链接**，但不要过多。
- **D-18:** 部分特殊属性与**地图伤害实际结算**尚未内置，用户会在编写文档前补齐；写作以当时代码为准。
- **D-19:** 标注「占位 / 待提供」的示例，待用户提供后再写。
- **D-20:** 阅读顺序（4 + 8 + 9 + 3 = 24 篇）：
  - 概念与导航：`data-vs-render`、`src-tour`、`code-basics`、`hooks`
  - 基础接口：`data-state-overview`、`hero-attribute`、`hero-items`、`hero-equipment`、`hero-location`、`map-structure`、`map-tiles`、`flags`
  - 战斗：`combat-overview`、`enemy-specials`、`enemy-aura`、`enemy-query`、`enemy-final`、`enemy-calculator`、`enemy-map-damage`、`enemy-combat-script`、`enemy-status-hooks`
  - 其他：`events`、`replay-commands`、`data-plugins`

**逐篇内容**

- **D-21:** （概念·`data-vs-render`）数据端负责「算」、渲染端负责「画」；比喻「棋局 / 账本」对「棋盘 / 摄像机」；两者分别在 `src/data`、`src/client`；只讲好处，重点**录像验证**（只跑数据端）；附 mermaid 图；**不提**「渲染端不能反向推送」（留高级）；不提「后续再讲」。
- **D-22:** （概念·`src-tour`）详讲 `src/data`、`src/client`、`src/content`、`src/constant.ts`；**一句带过** `src/bootstrap.ts`、`src/data.ts`（数据端入口、需外部 bootstrap）、`src/package.json`、`src/styles.less`（一般不需要动）；**不讲** `src/main.ts`、`src/App.vue`、`src/types/`（均已弃用）；含一张「该不该改」表。
- **D-23:** （概念·`code-basics`）顺序 ①简明语法 ②模块与引入 ③类型入门；类型把**泛型比喻成「类型的函数」**；讲 `interface` → `implements` 约定（**建议但非强制**，不遵循也不会出问题）；三者都大概讲；结尾给 JS/TS 教程链接 `https://h5mota.com/bbs/thread/?tid=1018&p=3#p41`（该教程针对本引擎设计、更适合本引擎作者）。
- **D-24:** （概念·`hooks`）钩子是什么；常用钩子族一览；**需求 → 钩子对照表**（核心）；`addHook` / `removeHook`；`hook/initialize.ts` 一笔带过；async 钩子只提哪些是；「钩子可能被非本对象触发」简说一句（多主对象时才需要判断，一般不会串）。
- **D-25:** （基础·`data-state-overview`）数据端主对象 `state` 是访问一切入口；一张表列常用对象与获取方式：`hero` / `maps` / `flags` / `enemyManager` / `enemyContext` / `combat` / `eventSystem` / `pathfinding` / `tileStore` / `itemStore` / `mapStore` / `eventStore` / `faceManager` / `roleFace` / `replaySystem` / `loader` / `loadManager` / `getDataPlugin(id)` / `emitTip(...)`；按 L0–L3 **轻量分组标注**（分层不影响接口使用，细讲留高级）。放在基础接口组最前。
- **D-26:** （基础·`hero-attribute`）属性列表；基础 vs 最终属性（`getBaseAttribute` / `getFinalAttribute`）；改基础属性 `set` / `add` / `mul` / `div`（经 `getModifiableAttribute()`）；**修饰器**：内置 `ValueModifier`（数值加减，`@system/value`）与 `PercentageModifier`（**按基础值算百分比**，`@system/percentage`）；`addModifier` / `deleteModifier`；提 `save` 参数——**不进存档时，应由外部其它系统负责分配该修饰器，避免读档后不一致**；`getAttribute()` 只读、`getIsolatedAttribute()` 试算；示例：攻击 +N 永久、防御 −X% 临时；指回 hooks 篇。
- **D-27:** （基础·`hero-items`）`IHeroItems`（`addItem` 可传负数、`Pick` 立刻生效、`getItemState`、`iterateItems`、`useItem` 仅 `Constant` / `Consumable`、`itemCount`）；**四种类别区分**：`Constant`（永久）/ `Consumable`（消耗）/ `Pick`（即捡即用）/ `Equipment`（装备，虽是道具但属单独系统）；道具效果提一句属**内容层**，并说明道具效果可调用哪些内容（`state`、道具数据）；示例：发黄钥匙 / 减道具 / 使用道具。
- **D-28:** （基础·`hero-equipment`）`IHeroEquipment`（`slots` / `canEquipTo` / `equip` 含 `autoUnload` / `unequip` / `equipped` / `getEquipped` / `getEquips`）；`IHeroEquipsStore`（`add` / `delete` / `get` / `instancesOf` / `instances` / `count`）；`IEquipmentState` 的 `value` / `percentage`（本质是修饰器）；`compareEquip` **简单讲**；**排序器不讲**（高级）；以「会用常用接口」为界。
- **D-29:** （基础·`hero-location`）只讲**获取位置**（`hero.location` 的 `x` / `y` / `direction`、`hero.getLocation()`）与**获取楼层**（`floorId` / `map`）；移动位置、切换楼层留高级。
- **D-30:** （基础·`map-structure`）`IMapState` 楼层集合（`maps` / `getMap` / `getActiveMap` / `iterateAllMaps`）与**楼层激活**（active）；`IGameMap`（`layerList` / `eventLayer` / `tileStore` / 宽高）；`IMapLayer`（`alias` 别名、宽高）；**事件层本质就是个图层，归本篇**。
- **D-31:** （基础·`map-tiles`）只讲 `getBlock` / `setBlock` / `removeBlock` / `putMapData` / `getMapData` / `iterateBlocks`；`getLocationData` 属低级需求，**留高级**。
- **D-32:** （基础·`flags`）全局**可存档**变量系统；**所有接口都讲（含 `occupied`）**：`setField` / `getField` / `getOrInsert` / `getOrInsertComputed` / `deleteField` / `setFieldValue` / `addFieldValue` / `getFieldValue` / `getFieldValueDefaults`；会进存档；**建议**不滥用、不用的变量及时 `deleteField`；示例：记录开关 / 计数。
- **D-33:** （战斗·`combat-overview`）伤害大致怎么算；流程（基础数据 → 光环 / 查询 / 最终 → 伤害计算 → 战前脚本 → 战斗 → 战后结算 + 状态钩子）；mermaid 图；末尾「流程步骤 → 对应文档」对照表；临界值不在本篇提。
- **D-34:** （战斗·`enemy-specials`）特殊属性是什么、在数据里的样子、两类定义（无参 `defineNonePropertySpecial` / 有参 `defineCommonSerializableSpecial`）；`src/data/enemy/special.ts` 注册；**如何自定义新特殊属性**（步骤）；**「属性实现位置」对照表**（内置属性各自实现在哪）；**多个示例**（有参 / 无参、`name` / `desc` 用字符串与函数）；编辑器识别约定（`// {code} - {name}`、`/** {code} - {name} */`、`ISpecial{code}Value`、`#region` 不能删）；**怪物比较**简单说、一般不改、真要改参考高级教程。
- **D-35:** （战斗·`enemy-aura`）**先讲优先级**（高优先级可影响低优先级、反之不行；与查询效果共用优先级）；内置光环（普通 23 / 支援 24 / 特殊光环 26）；运作方式（写「转换器 + 视图」并注册，**不深讲为何**）；四种内置范围只列名（`FullRange` / `RectRange` / `ManhattanRange` / `RayRange`）；**多个自定义示例**：基础光环（减少周围怪物金币与经验）+ 高级特殊光环（给周围怪物上光环、优先级高于特殊光环）；借示例讲清基础光环 vs 特殊光环差距；`apply` 与 `applySpecial` 差别讲清。
- **D-36:** （战斗·`enemy-query`）**新增内容（引擎未内置）**；解决「特殊属性查询外部状态」；常规查询 `CommonQuery`（`registerCommonQueryEffect(code, effect)`，`apply(handler, special, query)`）与特殊查询 `SpecialQuery`（`registerSpecialQueryEffect(effect)`，`for(ctx)` → 修饰器 `shouldQuery` / `add` / `delete` / `modify`）；与光环共用优先级；**三个示例**：抱团（范围内每有一个带该属性的怪物就给自身加成）、同化（把范围内怪物特殊属性同化到自身，数值型加算叠加、否则取位置索引最小者）、号角（场上每有一只怪物就给自身加成）；说明三者能干什么即可；用**抱团**对比「用光环实现复杂度更高」；设计原因留高级。
- **D-37:** （战斗·`enemy-final`）最终属性效果：**只影响自身、不依赖也不影响外部环境**的一段收尾调整；内置坚固(3)、模仿(8)；接口 `IEnemyFinalEffect`（`priority` + `apply`）、`registerFinalEffect`；**三方对比**（光环：不依赖外部但影响外部；查询：依赖外部仅影响自身；最终：两者皆无）；示例：**仿攻**（怪物攻击 = 玩家攻击）；`priority` 一句带过；回指 `combat-overview` 流程。

- **D-39:** （战斗·`enemy-map-damage`）概念（领域 / 夹击 / 阻击 / 激光 / 伏击）；三部分（伤害视图 / 转换器 / 合并器，浅讲）；注册 `useConverter` / `useReducer`；内置五类表（`code` / 实现位置**写文档时核对源码**）；自定义示例：**受地形遮挡的激光**；合并器简单讲（决定一个点受多个地图伤害时取什么伤害类型，深入留高级）；**实际结算用户届时补**。

- **D-42:** （其他·`events`）只讲**如何自定义新事件**（内建函数），不讲原理、不列内建全量；`BuiltInFunction`（`name` + `func(param, env)`）；`IBlockEventEnv` 常用字段（其余指向 API）；参数接口在 `types.ts`；注册在 `createEventRegistrations()`；内置示例导读；**自定义示例：设置 flag、勇士回血**；编辑器识别方式未设计完 → 文档留余地。
- **D-43:** （其他·`replay-commands`）录像系统用途 + **核心原则**「玩家直接产生、会影响最终成绩的行为必须计入录像」并解释其含义；**如何新增自定义录像需改 `packages-user` 下的引擎内容**；主动录像 vs 被动录像（`ReplayCommandType.Active` / `Passive`）；`@shouldReplay` / `@ignoreReplay` 的功能与检测（`begin` / `end` 区间）；**不给示例**，后续其他教程引入自定义录像时直接链接过去。
- **D-44:** （其他·`data-plugins`）插件是强拓展系统，中级只讲基础、**高级教程详解其工作原理**；`IDataPluginDefine`（`id` / `dependencies` / `awake` / `initialize` / `afterLoad`）；时机次序 `awake`（装配）→ `initialize`（**加载前**）→ `afterLoad`（加载后）；注册在 `src/data/plugin/list.ts` 的 `dataPlugins`；`state.addSaveableContent`；示例**占位**（待用户提供**较简单**插件，**不用商店插件**）；写明「是否纳入本中级篇取决于示例难度」。

### 文档写作流程（长期规范，适用于后续所有文档写作，不止本批）

- **D-45:** prettier 格式化。文档写完后**必须**跑 prettier 格式化——prettier 也管 markdown；不格式化虽不报 eslint 错，但用户日后手动修改会产生大量格式变动。推荐命令：`node node_modules/prettier/bin/prettier.cjs --write "docs/intermediate/*.md"`（或等价的 `pnpm exec prettier --write`）。若格式化会阻断某条命令执行，**先跳过并在对话中提出**，由用户自行格式化。
- **D-46:** 两阶段修订循环。修订必须依次经过两阶段，缺一不可：
  1. **独立读者提问循环**：派一个与写作者不共享上下文的子代理，按目标读者的前置阅读顺序阅读文档（先读前置教程，再读本次文档），**只读文档，不读源码**。子代理的任务不是审阅、不是判断对错，而是以读者身份提出「读完后仍无法从文档中得到答案」的问题；每条问题附上所在位置、已经从文档知道什么、还缺什么。子代理**不得**指出文档错误、不得提修改方案、不得做正确性判定。计划文件的质量检查（如 plan-checker）仍按 GSD 流程执行，不属于本条读者审阅。
  2. **用户主导的修订循环**：用户以更贴近本领域的视角提出问题 → AI 派子代理逐条修改文档 → 回报 → 用户继续提，直到用户满意并确认。
  **审阅记录只追加、不覆盖**：每轮新增带轮次标题的记录，历史轮次逐字保留；不得用后一轮内容覆盖前一轮。轮次可写在同一文件的追加小节，也可每轮独立成文件。
  **读者问题过滤**：只接纳正常定制流程中实际会遇到、容易触发或容易理解错的问题；假设性、极低概率、需要刻意构造的边界不进入修订清单。教学文档不追求面面俱到，样板已内置的异常与边界由 logger 错误码承担，正文不逐条枚举。写作者与用户可判定某问题「不写入文档」。
  **审阅范围**：只审本次目标文档；已由用户审阅并验收的前置文档（如中级、高级 I / II）不重复审阅。
  **文档正确性由写作者与用户负责，不由独立读者负责。** 必须经过用户循环且获用户确认后才可收尾，不得由 AI 自行收尾。适用于后续所有文档写作。
- **D-47:** 高级教程预留，修订 D-16。凡「留到高级教程细讲」的内容，必须**显式说明**并**预留链接标记**。由于 `docs/advanced/` 尚未建立，**不得**写指向它的真实 markdown 链接（会造成死链、构建失败）；改用非断链占位（如代码 span `高级教程 · <topic>` 或 `<!-- TODO(advanced): <topic> -->`），待高级教程存在后再替换为真链接。此条在「高级教程引用」范围内取代 D-16 的「禁元叙述」。
- **D-48:** 实操写法，长期规范。系统/原理讲解保持现状（可以讲、且现在这样就好）；需要重做的是**「实操/示例」部分**。每处实操统一写成可分步照抄的形式：
  1. **目标**：先说要做出什么效果；
  2. **改哪里**：哪个文件、文件内哪个位置；
  3. **复制什么**：只给要新增的那段，**不含 `import`**；写清「顶部通常已有这些 import，不要再粘；若报缺少 X，再在顶部补 `import ...`」；
  4. **改什么**：复制后只需改的数值/字段/名称；
  5. **怎么验证**：改完看什么现象；
  6. **注意**：常见错误、别碰什么。
  另外：示例取**最短可行**（如「下次战斗伤害翻倍」直接用 `onAfterCombat`，不额外写战后脚本）；**不写 `dev.md` 的引擎开发约定**（如 import 必须置顶、注释位置等）；**不写发布前/数量类无关信息**（如「发布前会有约 100 个内置事件」）。适用于后续所有文档写作。
- **D-49:** 示例与「改内置优先」。
  1. 示例代码必须**贴合引擎现状**：定义 `class` 再 `new`，**不要**写 `const obj = { ... }` 这类 plain object（引擎代码即如此）。例外：引擎本身就以对象字面量声明的内容（如 `src/content/item.ts` 的 `ItemEffect`），可沿用其现有写法。
  2. 文档主体应主要讲**如何改内置类**（如 `src/data/enemy/*`、`src/data/hook/*` 中已有的类）；在**末尾**再简述「何时需要自己新写类、怎么写」。
  3. 必须明确写明：**如果你不怎么懂代码，建议直接改内置，而不是自己写新的类。**
- **D-50:** 通用模板 vs 示例。对每类可扩展机制，文档要提供的是**机制本身的通用模板**，而不是某个具体效果的模板/示例：
  1. 单独一节（如「模板：复制什么、改什么」），给出一段可复制的**骨架**（类 / 转换器 / 视图 / 效果等），并用 `[需改]` 标出作者需按自己需求修改的部分；
  2. 模板与示例**分开**，不要把某个特定效果（如某个具体光环）当作模板；
  3. 示例仅用于辅助说明，尽量短。
  示例：光环应给「光环转换器 + 光环视图」的通用骨架 + 需改点，而不是给「减少金币经验的光环」当模板。
- **D-51:** 特殊属性实现的落点与讲解方式。
  1. **不要建议新建文件**：已有实现文件（如光环的 `src/data/enemy/aura.ts`）就全部写在其中，不要建议「新增一个自己的文件」。样板集中放置是为了方便管理与后续编辑器自动识别；只有**查询属性**需要单独新建 `query.ts`。
  2. 对 `aura.ts` / `query.ts` 这类独立的特殊属性实现，建议用 `#region` 包裹，结构更清晰、后续编辑器也可能据此识别。暂定识别约定：`//#region {code}-{name}` … `//#endregion`。
  3. 必须用**通俗语言解释「副作用」是什么**（刚接触代码的作者不懂这个概念）。
  4. 说明**地图伤害是按「计算后怪物」计算**的：因此若光环给怪物新增了「领域」这类属性，该怪物确实会有领域效果；旧样板无法动态给怪物加特殊属性，这一点值得单独说明。若某种属性确实既要依赖外部环境、又要修改外部环境，应拆成「查询效果 + 光环效果」两个，二者通过新增一个怪物属性桥接（指向高级教程）。
  5. `getCriticalLimit` 一般用不到，提一句即可，并说明高级教程会详细讲。
  6. **接口讲解方式**：不要上来就搬接口列表；先说「为了实现 X，我们需要修改 Y 接口」，再讲这个接口的参数，这样更自然。
- **D-52:** 加粗边界，长期规范。`**加粗**` 的内容**不要以标点开头或结尾**（CommonMark emphasis 边界规则会导致不渲染）。若确需加粗含标点的短语，应调整结构，使 `**` 相邻处为标点/空白，或改用 HTML `<strong>`。提交前用 flanking 规则自检所有 markdown。适用于后续所有文档写作。
- **D-53:** 高级教程分层。高级教程本身按**难度/深度**（而非领域）分为 **I / II / III** 三层（避免与顶层「初级/中级/高级教程」撞名）：
  - **I（基础扩展）**：较低门槛，核心为插件系统与基本扩展机制；
  - **II（深入定制）**：中等门槛，需要理解并修改引擎的特定系统（主题不固定，可能落数据端也可能落渲染端）；
  - **III（原理与架构）**：最高门槛，系统性讲解设计原理与架构。
  由于渲染端尚未完工，**当前只规划/编写数据端内容**。分层是**难度标签，不是领域分类**；具体主题可能在层间调整。
- **D-54:** 高级教程定位。文档面向**使用者**（不是引擎编写者）：在适度解析的同时，必须告诉读者**怎么用、怎么改、怎么自定义**；仍沿用 D-48（实操六步）、D-49（改内置优先/类示例）、D-50（通用模板单独成节）、D-51（落点/副作用/接口讲解方式）、D-52（加粗边界）等规范。
- **D-55:** 优先插件。明确建议：**新增系统优先通过插件系统实现**；只有不得不修改内置系统时才去改内部。理由：版本迁移时 `src` 基本不会改，但内置包（`packages` / `packages-user`）有可能会改，改内置会增加升级时的维护成本。
- **D-56:** 高级 I 内容，7 篇。
  1. **高级 I 导览**：I/II/III 分层、阅读路径与前置、D-55 原则；
  2. **声明式 vs 命令式接口**：旧样板命令式（写一行即生效）vs 新样板声明式（告诉系统要做什么，系统在合适时机执行）；必须讲透，作为后续基础；
  3. **插件系统**：自定义新插件、插件间调用、`dependencies` 依赖与排序、生命周期进阶、插件 id 稳定性与版本迁移；
  4. **可存档内容（`ISaveableContent`）**：存档一致性、三级压缩、注册存档对象、存档顺序 / `afterLoad` / `bindSaveableExecuter`、跨对象引用、结构化约束（structured-cloneable：Object/Array/number/string/boolean/null/Map/Set/TypedArray/ArrayBuffer 等）、必须返回经 `structuredClone` 的对象；
  5. **录像一致性**：`@shouldReplay` / `@ignoreReplay` 该写在什么方法/函数上、能保证什么、不能保证什么；自定义录像行为 → II，深层原理 → III；
  6. **data-common 的 Store**：讲清各 Store 存了什么，明确是**内容层原始数据**、运行时一般**只读**，修改很可能绕过存档/录像/一致性而引发问题；
  7. **钩子深入**：多对象场景（地图与图层）、如何判断「触发者是不是我关心的 map/layer」（身份校验）、同一钩子被多个对象复用、注册/移除与异步钩子。
  每篇仍保留「怎么验证」。
- **D-57:** 高级 I 读者修订循环。高级 I 完成后，**必须**再走用户主导的修订循环（D-46 第 2 阶段）；且这次的读者人格**不能复用中级教程的「不懂代码的游戏作者」**——应面向**对代码有一定了解、了解基本语法（变量/函数/类/import 等），但代码能力一般、不熟悉引擎内部架构**的作者（既不是完全不懂代码，也不预设过高的代码水平；代码能力一般的作者同样需要高级定制内容）。**高级 I 用较低标准，高级 II / III 可适当提高标准。**具体人格在计划中明确，并经用户确认。
- **D-58:** **D-49/D-50 的「改内置还是自己新增」取舍与「必须提供通用模板章节」只适用于中级教程。** 高级教程**不强制**提供模板章节：是否提供视文档内容而定（有些可以加，有些不用加）。高级教程的取舍原则仍是 D-55（优先插件、必要时才改内置）；不要求逐字写「不懂代码就改内置」这类中级提示。
- **D-59:** **高级教程写作风格（修订 D-48 在高级教程中的适用）：** 高级教程按**一般库文档**的方式写（但读者门槛略低于一般库文档，需要多解释概念），**不再使用中级教程的「复制什么 / 改什么」六步实操**，也不要把读者当成什么都不懂。
  - 提供**示例代码 + 注释解释**即可：先说明要做什么，再给出完整示例（含解释性注释），最后说明如何在需要的地方加载/接入（注释标明写在哪里）。
  - 保留必要的概念解释与验证，但用叙述方式，不要步骤化说教。
  - 不写「如果你不怎么懂代码」这类提示（与 D-58 一致）。
  - 适用于高级 I / II / III。
- **D-60（简洁优先，长期规范）：** **文档不是讲得越多越好。** 所有文档的核心目的是让读者知道「怎么用接口」；理解原理也只是为了更好地用。判断标准：
  - 能删的就删，避免面面俱到；
  - 不重复其他教程（如中级已讲过的内容）已经讲清的内容；
  - 对「几乎不可能需要自定义」的内容（如 Store），只讲内置接口怎么用，不展开「自己写」与验证；
  - 高级教程尤其要克制：按库文档方式，只保留读者真正需要的说明与示例。
  适用于后续所有文档写作。
- **D-61（主干与边界分离，长期规范）：** 文档的**主干只讲最核心的内容**；**边界情况、特殊情况不要混入主干**，应在文末**单独开一节**（如「边界与注意」）集中说明。适用于后续所有文档写作。
- **D-62（代码块结构完整，长期规范）：** 文档中的代码块必须是**完整、结构正确的片段**（完整的类 / 函数 / 文件级片段），能让语法高亮正常解析；**不要单独写某个类成员或脱离上下文的片段**。必要时用注释省略无关部分，但仍需保留结构完整。适用于后续所有文档写作。
- **D-63（模板的组织顺序，长期规范）：** 模板**不要放在文档最开头**。正确顺序是：先讲**理念/概念**（要解决什么问题、可以做哪些扩展）→ 再给引导语（「如果想……，可参考下述模板」）→ 模板代码 → 解释模板做了什么、声明了什么类、实现了什么接口、需要自己改什么。适用于后续所有文档写作。
- **D-64（模板 vs 纯接口，长期规范）：** 只有**需要读者自己实现接口或注册内容**时，才提供完整模板；**纯接口使用**（如 Store）只给示例，不给模板。适用于后续所有文档写作。
- **D-65（示例注释，长期规范）：** 示例代码**必须加解释性注释**；注释**越多越好**，以降低读者的理解难度。适用于后续所有文档写作。
- **D-66（杂类功能的示例分开写，长期规范）：** 对内容较杂的功能（如多个 Store 并列），**示例必须按功能分开写**，一个功能一段示例，**不要合并成一大块**；示例应与它所讲的功能**直接对应**。适用于后续所有教程文档的编写。
- **D-67（高级 II 内容，暂定）：** 高级 II 定位为「**深入定制**」（难度层，非领域分类）。**本规划为暂定**，后续可能调整（例如发现高级 I 仍有遗漏内容时），当前先完成高级 II。高级 II 也需要一篇**导览**。拟含 8 个主题 + 导览：
  1. **高级 II 导览**：本层难度定位、前置（高级 I + 中级相关篇目）、阅读路径；
  2. **自定义范围对象**：`IRange` / 范围参数 / 绑定宿主；被光环、地图伤害等复用；
  3. **静态图块与动态图块**：两者区别与转换；**专门讲点事件与图块事件**；
  4. **勇士的装备系统**：装备实例仓、修饰器、排序器、`compareEquip`、装备事件；
  5. **自定义录像指令**：指令码、`IReplayCommand`、主动/被动、注册与沙盒播放；
  6. **自动寻路**：只讲流程（构建图 → Dijkstra 求路径 → 交给移动器），不讲算法细节；
  7. **新增勇士属性**：修改 `IHeroAttr`；示例用**攻速**（每回合造成 `atkSpeed%` 伤害）与**护甲**（战斗百分比减伤）；接入修饰器/伤害计算器；编辑器新增项、状态栏显示等按 D-47  **留空**；
  8. **新增怪物属性**：修改 `IEnemyAttr`；同样用攻速/护甲举例；接入战斗/光环/查询；编辑器新增项、怪物手册（图鉴）修改按 D-47 **留空**；
  9. **怪物上下文与战斗深入**：buildup 管线、优先级、缓存/脏标记、伤害系统与光环/查询/最终的交互。
  推荐顺序：导览 → 范围对象 → 图块（含点事件/图块事件）→ 装备 → 录像指令 → 寻路 → 勇士属性 → 怪物属性 → 怪物上下文与战斗。仍以数据端为主；渲染端与编辑器内容按 D-47 占位。
- **D-68（高级 II 读者水平）：** 不要给高级 II 读者预设过高的代码水平。目标读者应设定为：**已经理解了绝大多数常用语法；认真阅读样板后，能把一部分简单系统和中等复杂度的系统读明白**。审阅人格与文档难度均按此标准，而不是按「资深引擎开发者」预设。
- **D-69（纯内部实现章节，长期规范）：** 讲解**纯内部实现**的章节，开头必须写明「此章节讲解一下 XXX 的内部实现」；这类章节应放在文档**靠后**位置，文档前面以「如何使用」为主。适用于后续所有文档写作。
- **D-70（代码块完整类上下文，长期规范）：** 代码块必须包裹**完整的类上下文**（尤其是类的方法），确保语法高亮正确；不要单独展示脱离类的方法体。适用于后续所有文档写作。
- **D-71（高级 I 待补内容）：** 高级 I 还有未讲内容，待后续补写：**移动 Mover**、**FaceHandler 系列接口**。当前先完成高级 II，之后再补。
- **D-72（注释优先，长期规范）：** 当引擎源码的**注释与实现不一致**时，文档**一律以方法注释为准**，并在对话中**向用户报告**该不一致。不得按实现去改写注释的语义。**该不一致只在对话中报告，不写进文档正文。** 适用于后续所有文档写作。
- **D-73（假定编辑器已完成，长期规范）：** 文档**假定编辑器已经完成**。涉及编辑器 / `.jsonc` 内容配置的地方，只写「需要编辑器」的占位标识；**不要讲「编辑器未就位时改文件、就位后用编辑器」**这类过渡做法。所有 `.jsonc` 均由编辑器负责。适用于后续所有文档写作。
- **D-74（章节锚点链接，长期规范）：** 引用其他文档的**具体章节**时，使用 `./xxx.md#标题` 直接定位到该标题（如 `./static-vs-dynamic-tiles.md#双向转换`）。适用于后续所有文档写作。**待办：** 高级 II 完成后，回头检查高级 I 与中级教程是否存在同类未定位的链接。

  两篇按高级 I 读者水平（D-57：了解基本语法、代码能力一般）与库文档风格（D-59..D-74）编写；渲染端 / 编辑器内容按 D-47 占位。补写完成后同样走独立读者审阅 + 用户修订循环（D-46 / D-57）。
- **D-76（面朝朝向 vs 移动朝向）：** 文档必须明确区分**面朝朝向（`faceDirection`）**与**移动朝向（`moveDirection`）**。`IObjectMover.forward` 的「沿当前移动方向」指的是**面朝朝向**走（不是 `moveDirection`）；`onSetMoveDir` 的「设置朝向」指设置**移动朝向**。源码实现正确，不得把此处注释当作 bug。
- **D-77（文档重心由内容性质决定）：** 文档重心**不是一律讲「怎么用」**，而由所讲内容的性质决定：
  - 样板**已提供、只需使用**的内容 → 重点讲**怎么用**（自定义概率极低，最多一两节带过）；
  - 内容本身就是**靠自定义 / 扩展**实现的 → 重点讲**怎么自定义**。
  二者不冲突。写作后自问：**这篇文档每个章节被使用的概率有多大？** 通篇低概率说明写得不好（除非文档本身就是讲底层自定义）。**若无法判断重心，先问用户，不得自行决定。**
  适用于后续所有文档。
- **D-78（审阅须给出章节使用概率）：** 独立读者审阅时**必须为每个章节给出「被使用的概率」**（高/中/低，并简述理由），让修订者知道哪些重要、哪些可以删减或后置。适用于后续所有读者审阅。
- **D-79（不写使用概率元信息）：** **不要在文档正文写「本节使用概率很低」之类的元信息**。但若某章看起来很有用、实际根本用不到，可以适当提示。适用于后续所有文档。
- **D-80（不写源码叙述）：** **不要在文档里写「源码怎么怎么样」**。文档是给人看的，源码级叙述对读者无用。适用于后续所有文档。
- **D-81（不把用户问题写进文档）：** 用户提出的是**问题**；**不要把问题本身或「为了解决该问题所以这样写」写进文档**。文档面向读者，不是写给用户看的复盘。适用于后续所有文档。
- **D-82（先讲系统模型）：** 讲一个系统时，**先讲清它的模型是什么**（概念、组成、数据流），再讲接口与用法；不要一上来就讲怎么获取、怎么调用。适用于后续所有系统类文档。
- **D-83（高级教程不写模板/需改标记）：** 高级教程中**不再写「模板」「[需改]」等标记或模板章节名**；示例代码只需用**注释说明下一行在做什么**。注意区分：游戏数据领域的「怪物模板 / 原始模板 / 默认模板」等术语不受此限。适用于高级 I / II / III。

### 文档写作概念补充（2026-10-26）

- **D-84（行文思路）：** 文档按**读者的理解顺序**组织，不按代码目录或接口清单组织：先给读者要解决的问题或场景，再讲系统模型（角色、分工、数据流），然后讲机制与设计理由，之后才是接口、用法和完整示例，最后用少量边界收尾。
- **D-85（文档与样板的关系）：** 写文档前必须先理解样板完整的**设计思路、调用链和生命周期**，不能只读被讲到的那一段代码；否则文档可能局部正确、整体却与项目脱节。文档要结合样板实际怎么构造、怎么运行，但不能写成源码导读或行号注释。
- **D-86（章节过渡与拆分）：** 每节只回答一个问题；不同消费者、不同阶段要分开讲，不能在同一节里来回跳。**只在认知跳跃大的地方**用 1–2 句说明「接下来讲什么、由谁负责、与上文什么关系」；自然承接的段落不硬加过渡。
- **D-87（示例写法）：** 示例服务于机制理解，必须完整、与正文概念对应；优先给完整类或完整函数，并用注释解释关键行为，而不是堆接口演示。由编辑器产出、作者不会手写的内容（如事件脚本），不要给手写代码示例。
- **D-88（详略与长度）：** 篇幅由内容决定。原理与架构层必须讲透设计理由、对象职责和数据流；不能为了「精简」删掉核心模型，也不能为了凑长度堆接口表和边角。只写常见、容易触发或容易误解的边界，其余交给引擎告警/日志。
- **D-89（正确性责任与审阅）：** 文档正确性由写作者和用户负责。独立读者只读文档、按前置顺序阅读，只提出「读完后仍无法从文档得到答案」的问题；不读源码、不判断对错、不提修改方案。审阅记录只追加、不覆盖。
- **D-90（提交节奏）：** 文档修订循环中**不逐轮提交**；由用户明确确认后，再统一提交一次。
- **D-91（独立读者人格审阅是内部循环，记录不交用户）：** 读者审阅只用于验证目标读者能否只靠文档完成 UI 编写，属于内部质量环节，不是用户审阅。
    1. **读者**：与写作者不共享上下文；只读 Markdown，不读源码，不做 live；只提出「读完后仍无法从文档得到答案」的问题，不判断对错、不提修改方案。
    2. **派发**：由 orchestrator 分别派发多个独立读者（按 Part/篇目分组），**不得由一个子代理包办全部篇目**；每轮复审使用新上下文，不复用上一轮问题清单。
    3. **循环上限 3 轮**：每轮汇总后只修**阻断性问题**——缺前置、术语未定义、步骤缺失导致无法继续、明确矛盾、缺 import/入口等。设计取舍、风格、详略、是否补充内容不属于阻断问题，不当作缺陷。
    4. **复审与停止**：每轮修订后重新派读者复审；连续一轮无阻断问题即结束。3 轮后仍有阻断问题，停止并只报告受影响的页面/章节，**不向用户展示读者问题清单**。
    5. **记录**：每轮问题、分诊、修订、复审结论写入内部记录，append-only，带 `### 第 N 轮` 标题；不写入 docs 正文，不交给用户。
    6. **验收**：最终一轮无阻断问题；docs 通过构建/类型/lint；读者记录完整；未把读者问题当作用户裁决项。
- **D-92（用户审阅只看最终文档）：** 用户审阅与读者人格审阅相互独立；用户只审阅修订完成的最终文档。
    1. **输入**：只把最终 25 篇文档（及 live demo）交给用户阅读；**不提供**读者审阅记录、问题清单、分诊表、修订日志。
    2. **意见**：用户按自己的阅读/使用体验提出意见；每条由用户裁决「改 / 不改 / 改成什么」；执行器只改用户点名内容。
    3. **独立性**：不得把读者问题转成用户待裁决项，也不得用读者问题替代用户审阅。
    4. **收尾**：循环直到用户明确确认；用户确认前不写 SUMMARY、不改 ROADMAP/STATE、不宣称完成。
    5. **验收**：用户确认原文 + 独占标记；最终门禁通过；文档为最终版。
- **D-93（文档深度：讲清模型、事件与组件，禁止只给“能干啥/参数表”）：** 本批 UI 文档必须让读者能自己写出 UI，而不是照抄；只列能力和参数不算讲清楚。
    1. **渲染树模型**：必须讲清根/容器/子元素的树结构、坐标与变换如何沿树传递、`zIndex` 与绘制/命中顺序、元素生命周期、缓存/脏更新与渲染树的关系，以及组件如何映射成渲染树。
    2. **事件模型**：必须讲清命中测试、捕获与冒泡的顺序、enter/leave 的特殊处理、`noevent` / `actionStroke` 对命中的影响、事件对象与嵌套容器中的传播；不能只列事件名。
    3. **元素与组件用法**：每个元素与内置组件都要讲具体使用方式、重要功能、典型组合与场景、注意事项和“为什么这样设计”，不能只写“能做什么 / 参数有什么”。
    4. **示例与解释并重**：示例要服务于机制理解；每次给出代码后解释它在渲染树 / 事件 / 组件模型中的位置与理由，不能只给可复制代码。
    5. **修订传递**：10-49 读者循环与 10-50 用户修订的修订者，除了审阅结论，还必须收到本条要求；修订与复审时同时检查“是否讲清模型、事件与组件用法”，不能只修列出的问题。
    6. **验收**：读者能复述渲染树、捕获/冒泡、组件拆分与 props/slots/attrs 的作用；能独立改写示例，而不是只能照抄。
- **D-94（读者审阅的标准阅读范围与顺序）：** 读者审阅必须**先完整读完目标文档之外的全部文档**，再读目标文档；不得读任何其他内容。
    1. **先读非目标文档**：按文档站的前置顺序读完目标之外的全部文档（本批为中级 → 高级 I → 高级 II 现有数据端 → 高级 III，以及其它非目标文档），目的是知道哪些概念、入口、约定已经在别处讲过。
    2. **再读目标文档**：本批目标为 `docs/advanced/ii/ui/` 下的 25 篇，按 Part 0→5 顺序读。
    3. **只对目标提问**：问题只针对目标文档；可以引用非目标文档说明「这里已经讲过 / 与前文冲突 / 前置不足」，但不得把非目标文档本身当成审阅对象。
    4. **不得读其他内容**：不读源码、不读计划、不读旧文档、不读上一轮审阅记录、不读无关文档；避免用代码或实现污染读者上下文。
    5. **每轮适用**：Round 1/2/3 的每个新读者都必须执行本顺序；不得只读目标文档或只看导览。
    6. **验收**：读者记录必须列出「读过的非目标文档 + 目标文档」；未读非目标文档的审阅记录无效，需要重跑。
- **D-95（结构/流程必须配 mermaid 图）：** CONTEXT D-01 已允许 mermaid（`vitepress-plugin-mermaid` 已安装）；本批 UI 文档必须实际使用，不能只用段落描述结构或流程。
    1. **必须用图的场景**：渲染树/元素树、坐标与变换/`zIndex`/命中顺序、事件捕获/冒泡、UI 栈与打开关闭、组件数据流与 props/slots/attrs、完整示例的步骤与组件拆分、缓存/脏更新流程。
    2. **位置与篇幅**：图放在对应机制小节开头或示例前，配 1–3 句说明；图与正文不重复废话。
    3. **格式**：使用 VitePress 的 ` ```mermaid ` 代码块；不引入新依赖。

    2. **预览尺寸**：文档站 live 可用任意预览尺寸（如 480×320），但**正文不写预览尺寸说明**；live 只负责展示效果，不要求与真实画布一一对应。
    3. **独立面板**：可以有自己的设计尺寸，但必须说明它不是游戏画布尺寸；不要把它和 `FULL_LOC` 混用。
    4. **修复节奏**：已经审阅/修改过的文档立即改为 `FULL_LOC`；尚未审阅的文档在后续审阅到该页时再改，不做全批批量替换。
- **D-97（文档不写修复说明/元叙述）：** 文档正文只写给读者看的内容；不写「之前讲过 / 已经改好 / 不要这样做 / 我修复了 X / 文档站没有环境所以这里不画图 / 不要现场 new Texture」这类修复过程、问题复盘或元叙述。用户反馈只用于修改文档，不把反馈或修复结论抄进正文。
- **D-98（容器裁剪与 `nocache`）：** 默认情况下，容器外的内容**不可见**；`nocache` 可能让超出容器的内容显示，但这是渲染实现的特性，后续可能变动，文档不得依赖或推荐。不得写「容器不裁剪 / 超出容器仍然可见 / 0×0 容器看得见但点不到」这类说法。
- **D-99（默认给混合方案）：** 用户说「也可以 X / 不要只给 Y」时，默认保留 Y 并加入 X，给出混合示例（如 `fill` / `stroke` / `fill + stroke` 三种），不要把 Y 全量替换成 X；只有用户明确说「全部换成 X」才全量替换。
- **D-100（文字页与后续不写元素层 TS）：** 文字页先讲 `Font` 字体类，再讲 `<text>` 用法；不再写独立的元素层 TypeScript 示例（`new Text()`、元素层导入、`Font` 静态调用代码块等）。需要构造 `Font` 时用 TSX 内联表达式或文字说明；后续文档同样只写 TSX 用法、live 与说明。文字属性要覆盖 `text`、`font`、`fillStyle`、`strokeStyle`、`strokeWidth`，并说明测量尺寸、锚点、对齐与不换行。

- **D-102（live 必须就近放置）：** 文档的 live 要放在对应知识点旁边，不能只在文末放一个综合 live。讲解法、字体、属性、锚点等每个需要看效果的小节，各自配一个 live；后续所有文档同样适用。
- **D-103（图片页只讲贴图管理器）：** 图片与纹理页只讲从 `props.state.materials` 取已登记贴图（`getImageByAlias`，必要时提 `getImage`），再交给 `<image>`；不讲 `new Texture`、手动加载、画布、URL 等其他来源。`hd` / `anti` / `noanti` / `noevent` / `alpha` 等通用属性留到后面集中讲，不在图片页展开。
- **D-104（文档修订前必须读源码）：** 每次派发文档修订子代理前，任务必须要求其先读相关 `props.ts`、元素/组件实现、管理器接口与现有用法，逐条核对可空性、默认值、属性行为；旧文档只作素材，不能当事实来源。执行器交付时附源码依据（文件:行号），主代理抽查；构建通过不等于语义正确。
- **D-105（应用场景必须有内在原因）：** 可以写应用场景，但必须能从属性语义、限制或代价推导出原因；不能假设“常用于/只用于”某场景。禁止没有逻辑链路的扩展（如为 `image` 造 `Icon` 子组件）。元素页仍不主动扩展工程封装等超范围内容。
- **D-106（层级/变换页范围）：** 通用参数页已覆盖 `zIndex`/`hidden`/`alpha`/`filter`；层级、变换与性能页只讲 `scale`/`rotate`/`transform`、`cache`/`nocache`、`composite` 与性能取舍，不讲 `noevent`/`type`/`fall`。`alpha`/`filter` 不是继承属性，但缓存父级会作用在整张缓存结果上，因此子元素会被一起影响；未缓存的父级不会把这两个属性传给子元素。
- **D-107（提问先回答，不直接改）：** 用户以提问语气询问原因、机制、现象或“是不是……”时，先解释/回答，不得直接修改文件或派发执行；只有用户明确要求修改后才动手。即使已经判断出可修项，也先说明并等待用户决定。
- **D-108（标题统一用名词短语）：** 文档 H2/H3 标题一律用名词短语，不用句子、祈使句或问句；例如「指令与分组」「数据到渲染」，不写「指令与分组定义在……」「数据变化如何走到……」。后续文档同样适用。已审阅的渲染系统文档统一扫描修正；用户尚未审阅的文档先不改。
- **D-109（按读者需求取舍内容）：** 写文档先想读者需要知道什么，而不是把知道的细节全写进去。重点是「怎么用、怎么运行、怎么写能运行、常见错误怎么处理」；不要堆砌罕见边界、极少遇到的异常处理、底层原理和无关细节。内容过多会让文档失去可读性，宁可少写、写清楚。
- **D-110（UI 示例必须遵循标准模板）：** 文档里的 UI 代码示例必须使用 `ui-template.md` 的标准结构。完整示例包含 imports、`MyPanelProps`、`myPanelProps`、`GameUI`、`FULL_LOC`；后续简化示例只能用 `// setup` + `// 组件内容` 的形式，不能写成 `export default defineComponent(() => ...)` 这类项目模板之外的 demo 包装。live 组件由文档渲染器挂载，不受此限；但文档正文不能把 live 包装当成 UI 入口写法。
- **D-111（value 双向绑定统一用 `v-model:value`）：** 任何组件的 `value` 双向绑定一律写 `v-model:value={...}`，不要写裸 `v-model`，也不要手写 `onUpdate:value`。其它 prop 的双向绑定写 `v-model:prop`（如 `v-model:page`、`v-model:selected`）。
- **D-112（渲染指南的后续重构）：** 自定义 UI / 画面绘制文档内容多且集中，不拆到不同阶段。当前审阅结束后另开计划：新增“渲染指南”专页，内部分为渲染基础、渲染进阶、渲染底层，按不同深度组织。**渲染指南只收“怎么画画面、怎么写 UI”的内容；与渲染关系不大的系统不迁入，仍留在中级/高级教程中。** 普通中/高级教程仍穿插画面/UI 内容，但只讲主要逻辑，不细讲原理和 UI 代码为什么这么写。每篇文档增加“前置知识”部分，列出必须先读的文档。当前先记录，不移动文档。
- **D-113（接口必须先说明是什么）：** 文档里出现任何接口、成员或类型时，必须先说明它的名称、类型/形态和用途，再讲它能做什么；不能只列接口名并假设读者已经知道。不要把引擎内部接口、内部成员写进用户文档；用户常用接口按使用频率放在主要位置，不要塞进“其他接口”。
- **D-114（excitation 执行顺序与 transition 端点判断）：** excitation 执行不同激励对象的顺序不保证；在 `onExcitedFunc` 中用“当前值是否等于 min/max 端点”来决定下一目标，可能在起始帧设置目标后、Transition 尚未推进时，下一帧又因当前值仍在端点而重复设置同一目标，导致动画永远停在起点。`Selection` 的 alpha 来回切换就是典型案例。这是系统“设置当帧不改变值”的既定行为，不是系统 bug，只能在实现层规避：不要用当前值等于端点作为切换条件，改用独立状态、方向变量或事件驱动；后续文档涉及 `Selection`、`Transition`、`onExcitedFunc` 动画时需专门提醒。
- **D-115（文档修改前的全量阅读，强制，不得再遗漏）：** **任何文档修改子代理在动手前，必须先按文档站阅读顺序完整读完目标文档之外的全部现有文档**：中级 → 高级 I → 高级 II 现有数据端/其他已存在篇目 → 高级 III → 其他非目标文档；读完后才能读目标文档和相关源码。**未完成全量阅读不得修改，不得以“只读了相关源码/目标页”代替。** 每次派发任务必须把本要求原文写入任务，并**明确说明阅读目的**：一是了解项目整体结构、已讲概念与文档分工，避免写出与现有内容脱节的说明；二是对齐文档的写作风格、详略、示例、标题、术语与表格形式，避免只读目标页造成风格偏差。**不得只列阅读清单而不说明目的，也不得把“读文档”本身当成任务。** 要求子代理在回报中列出已读文档范围及对结构与风格的实际判断；未列出、未读全或未说明目的的改动一律视为不合格，必须重做。此条与 D-94 的读者全量阅读要求并列，适用于所有文档修改子代理，**不得以时间、并行、上下文限制或任务简单为由跳过**。
- **D-116（文档编写豁免 GSD，用户主导的子代理循环）：** 文档编写/修改不再要求 GSD 的 Plan → Execute → Verify，不为此创建计划，也不派 `gsd-planner` / `gsd-plan-checker` / `gsd-executor`。但**文档仍必须由主代理派发子代理编写/修改**，不能由主代理内联落盘。流程改为「主代理派发子代理写/改 → 用户审阅 → 主代理按意见再派子代理修订」的循环；可随时中断和继续，不写 SUMMARY / ROADMAP / STATE，除非用户明确要求收尾或记账。**每次派发文档编写/修改子代理时，任务里必须明确要求它先读 `.planning/phases/10-docs-restructure/10-CONTEXT.md`（至少 D-115、D-116 和相关写作规则），再按 D-115 原文完成“现有文档全量阅读 + 明确阅读目的”，并在回报中列出已读范围与对结构/风格的实际判断；不得只把目标文档和源码给它。** D-115 的强制全量阅读适用于文档内容写作子代理；纯结构迁移/路径调整不强制全量阅读。内容准确性、源码核对（D-104）、写作风格、示例标准、标题/参数表等文档内容规则仍然适用。
- **D-117（可读性优先于绝对准确性）：** 文档解释概念、接口与行为时，优先使用读者能直接理解的语言和例子；**不得为了追求形式上的绝对准确而引入复杂公式、术语、冗长限定或底层计算过程**。能一句话说清就不展开“进度怎么算、当前值怎么插值、曲线终值如何代入”等读者不关心的细节；必要的技术说明放在不会增加理解负担的位置。贯穿所有文档、示例和“边界与注意”章节，不只是动画文档。
- **D-118（讲接口前必须先讲“为什么需要它”）：** **不得上来就介绍接口签名、参数和用法。** 每个接口（包括 `animate`、`to`、`curve`、`after`、`when`、`planEnd`、`bindExcitation`、`useAnimater`、`useTransition` 等）在正式说明前，必须先有一句上下文：当前场景要解决什么问题、为什么非它不可、不用它会怎样。没有这句引入就直接开始讲接口，视为不合格，必须补充。该要求与 D-117 一起适用所有文档。
- **D-119（“获取执行器/绑定”与“选择动画对象”分开）：** “获取执行器与绑定”指自己 `new Animater`、`bindExcitation`，或在组件里使用 `useAnimater`；这部分应放在计划模型之前，让读者先知道执行器从哪里来。`animate(content: IAnimatable)` 是“选择动画对象”，必须在计划模型之后再讲，并使用类似“为了让动画系统知道把当前值写进哪个对象，需要先绑定动画对象”的引入；不得把 `animate` 混入“获取执行器”小节。
- **D-120（指南文档必须一步步教，不能写成 API 参考）：** 复杂接口的指南文档**不允许**采用“先讲接口能干什么，再给一个完整大示例”的 API 参考写法。必须拆成使用顺序：为什么需要 → 先拿到什么对象 → 最小可运行示例 → 示例刚刚做了什么 → 下一步做什么 → 再给下一个示例 → 最后才是完整用法。简单接口可以短，但复杂接口（如 `transitioned`、`transitionedColor`、`cycledTransition`、Animater 编排）必须按步骤展开。所有指南文档都要按此自查。
- **D-121（术语首次出现必须解释）：** 任何专用名词（如“上游/下游”“激励源”“变速器”“插值”等）首次出现时，必须用普通开发者能理解的中文说明它是什么、在这篇文档里指什么；能不用术语就不用。不得假设读者已经知道术语含义。此条与 D-117 并列，适用于所有文档。
- **D-122（曲线模式只描述形状，不假设用途）：** `CurveMode` 和各曲线的说明只客观描述形状、速度分布、端点行为，**不得写“适合位移/淡入淡出/蓄力/脉冲”等使用场景假设**。读者自己决定用在哪里。
- **D-123（执行器状态机必须讲清）：** Animater 是状态驱动的执行器，文档必须说明哪些接口会改变内部状态（选择对象、设置曲线、写步骤、设置触发点、提交计划组等），以及 `to`、`query`、`wait` 等读取接口默认读取的是“当前计划组”“当前选中对象”“当前执行组”中的哪一种状态。不能只列接口而不讲状态依赖。
- **D-124（D-117 不删除必要的行为模型）：** D-117 反对的是读者不需要的底层实现细节，不是反对所有原理。读者理解用法所必需的行为模型必须讲清，例如曲线如何把时间进度映射为数值进度、执行器如何根据状态决定写哪个对象；用简单语言讲，不堆公式和实现细节。

- **D-127（教学参考材料位置）：** 用户提供的飞书教学文档已移动到 `.planning/references/feishu-teaching-docs/`。这些文档只作为行文思路、信息密度、示例与图示安排的参考，不作为当前项目文档的事实来源，也不要求照搬其结构、编号或标题。
- **D-128（标题只说明主题）：** H2/H3 标题使用短名词短语，只说明这一节讲什么；不得写成摘要长句、步骤式标题、口语化标题或“标题：解释”的冒号扩展。标题不是章节内容的核心，不承担概括整节的任务。
